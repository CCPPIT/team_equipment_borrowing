# 02 — مراجعة سلامة قاعدة البيانات
## النموذج والقيود
ثلاثة كيانات فقط: Employee وEquipment وLoan. الهوية UUID، والأوقات timestamptz(3)، والعلاقات FK تستخدم Restrict للحذف والتحديث. description وreturnedAt اختياريان. كل Loan يمثل وحدة واحدة؛ لا quantity أو status مخزن أو كيان Return إضافي.

Return يحدّث returnedAt للسجل نفسه ولا يحذفه. إعادة الاستعارة تنشئ UUID جديدًا وتحفظ السجلات السابقة. الفهرس الجزئي `unique_active_loan_per_employee_equipment` يمنع تكرار الزوج employeeId/equipmentId **حين returnedAt IS NULL فقط**. وCHECK يحصر المتاح بين الصفر والإجمالي ويمنع الإجمالي السالب. يوجد index على Loan.equipmentId.

هذه القيود المخصصة مثبتة في SQL migration، وليس في schema.prisma وحده؛ إعادة الإعداد يجب أن تستخدم migrate لا db push. فُحص catalog الفعلي للقاعدة الجديدة، مع تعريف القيود والفهارس وchecksum للترحيل في evidence/database-audit.log.

## التحقق من الصفر
أُنشئت قاعدة `team_equipment_final_phase05_test` مستقلة. نجح system:migrate من الصفر، ثم إعادة deploy بلا pending، وmigrate status أكد أن المخطط محدث. لم يتغير schema أو SQL أو migration_lock المعتمد في Phase05.

شُغل seed CLI مرتين ونجح؛ واختبار I17 المعاد يثبت أنه لا يصفر رصيد استعارة موجودة أو يحذف التاريخ عند التكرار. تنظيف fixtures يحصل في قواعد الاختبار فقط، لا في بيانات مستخدم حقيقي.

| الثابت | الدليل المنفذ |
|---|---|
| لا سالب أو تجاوز الإجمالي | CHECK في catalog، واختبارات I15 والمصالحة بعد الحالات |
| لا نشطين للموظف والنوع | D وI02/I10/I14، مع فهرس PostgreSQL حقيقي |
| كل Borrow وحدة وسجل واحد | A–C ورفض quantity في H01/I18 |
| Return يزيد المخزون مرة واحدة | F وI04/I11/I25؛ تكرار الإرجاع لا يغير التاريخ أو الرصيد |
| المعاملات الفاشلة لا تترك أثرًا جزئيًا | I06/I07/I08/I24 وH04/H05، ومنها فشل كتابة DB فعلي بعد الكتابة الأولى |
| التاريخ محفوظ | A–C وI03/I16/I17 مع هويات مستقلة وسجلات مكتملة |
| آخر وحدة لا تُستهلك مرتين | G1–G3: انتظار طلبين للقفل، ثم201/409 ورصيد0 ونشط1 |

Borrow وReturn يقفلان Equipment أولًا داخل ReadCommitted transaction. Return يعيد فحص Loan تحت القفل، ويشترط updateMany returnedAt=null وcount=1 قبل الزيادة. قراءة المعدات RepeatableRead تعطي snapshot متسقة دون حجز المخزون للمستخدم.

المراقب المستقل يفحص available+active=total وعدم السالب وفرادة موظفي النشط لكل نوع. هذا invariant يحميه بروتوكول التطبيق ومعاملاته، **وليس CHECK عابر جداول يحمي من SQL إداري خارجي**. triggers الفشل مؤقتة في قاعدة الاختبار وتزال في finally؛ catalog النهائي يثبت عدم بقاء أي منها.

بيانات التطوير متطابقة نصيًا قبل/بعد:3 موظفين و3 أنواع وصفر Loans، وأرصدة2/1/0. الأدلة dev-before.log وdev-after.log. إعادة التثبيت النظيفة استخدمت قاعدة جديدة أخرى، ولم تُعد تهيئة قاعدة تطوير أو إنتاج.
