# 07 — إجابات هندسية للشركة
## كيف صممت البيانات وحفظت تاريخ الاستعارة؟
ثلاثة كيانات: Employee وEquipment وLoan. المعدة نوع بوحدات متبادلة وله total/available، لا serial لكل وحدة. كل Loan وحدة واحدة وله borrowedAt وreturnedAt؛ null يعني نشطًا. الإرجاع يعدل السجل ولا يحذفه، وإعادة الاستعارة تنشئ UUID جديدًا. FK Restrict يحمي المراجع والتاريخ. اختبارات A–C وI03 تثبت ثلاث دورات مستقلة محفوظة.

## كيف منعت استعارتين نشطتين للموظف والنوع؟
يُفحص النشط تحت قفل Equipment داخل transaction، ومعه فهرس PostgreSQL جزئي unique على(employeeId,equipmentId) حيث returnedAt IS NULL. يسمح ذلك بسجلات مكتملة متعددة دون نشطين؛ unique عام على الزوج كان سيكسر إعادة الاستعارة. اختُبرت الخدمة والتداخل والفهرس نفسه في D وI10 وI14.

## كيف جعلت الاستعارة والإرجاع ذريين؟
Borrow يتحقق من الموظف ويقفل النوع ثم يفحص النشط قبل المتاح، وينقص واحدًا وينشئ Loan داخل Prisma.$transaction بعزل ReadCommitted. Return يقرأ هوية النوع ثم يقفل Equipment أولًا، ويعيد فحص Loan ويحدثه بشرط returnedAt=null وcount1 قبل زيادة واحدة. فشل أي كتابة يرد الجميع؛ H04 وH05 أحدثا خطأ DB فعليًا بعد الكتابة الأولى وأثبتا rollback.

## كيف تعاملت مع طلبين على آخر وحدة؟
كلاهما يطلب قفل صف Equipment نفسه. الأول يستهلك الوحدة ويثبت، والثاني ينتظر ثم يرى الرصيد الجديد ويرفض409 OUT_OF_STOCK. CHECK يحصر الرصيد. لا mutex محلي في ذاكرة عملية واحدة ولا retry mutation خفي. G1–G3 أرسلت HTTP عبر Next، ورصدت طلبين ينتظران Lock قبل الإفراج، ثم201/409 ونشط1 ورصيد0.

## لماذا هذا المستودع الموحد؟
apps/api وapps/web لهما مسؤوليات وبناء منفصلان، مع lockfile وscripts ووثائق في الجذر. npm Workspaces كان قرار Phase02 المعتمد؛ لم يتطلب التكامل تغيير مدير الحزم. لا shared package بلا حاجة؛ DTO صغيرة مستقلة ومطابقة بعقود واختبارات. الواجهة لا تستورد Prisma types أو خدمات الخلفية. التنظيم يناسب حجم المهمة دون microservices مصطنعة.

## لماذا Fastify وPrisma؟
هما من stack التكليف. Fastify يوفر JSON Schema validation وHTTP errors وinject للاختبارات، وPrisma يوفر عميلًا مكتوب الأنواع ومعاملات وترحيلات باستخدام adapter-pg. لا نفترض أن ORM يغني عن SQL: قفل FOR UPDATE مربوط المعلمات داخل tx، والقيود المخصصة في SQL migration ومفحوصة من catalog.

## كيف تتواصل الواجهة والخلفية؟
fetch نسبي إلى/api، وNext يعيد توجيهه إلى API_BASE_URL الخادمي. العميل يتحقق runtime من unknown إلى DTO. hooks بسيطة بلا state framework، مع مهلة وAbort/version وsnapshot employee وقفل ref. بعد النجاح أو التعارض أو النتيجة الغامضة تعاد قراءة GET، لا خصم متفائل أو POST تلقائي ثانٍ. health يقيس حيوية HTTP ولا يضمن جاهزية DB لكل طلب.

## كيف اختبرت قواعد العمل؟
15 unit للبيئة والأخطاء،33 integration لـFastify/Prisma/PostgreSQL تشمل القيود والـrollback والـlock wait،45 web للعميل والمكونات والحالة،19 system عبر HTTP مع مراقب SQL مستقل،و6 Chromium تتضمن keyboard وaxe. mocked fetch في اختبارات UI ليس دليل صحة المعاملات؛ الدليل من قواعد اختبار حقيقية منفصلة وسجلات فعلية.

## لماذا الموظفون seed ولا توجد مصادقة؟
لأن المطلوب موظفون جاهزون وإدارة الموظفين والمصادقة مستبعدتان. seed قابل للتكرار ويحفظ الرصيد والتاريخ القائمين. اختيار اسم ليس إثبات هوية، ولا نقدمه كتطبيق عام آمن دون قرار منتج وأمان منفصل.

## ماذا ستحسن إذا توفر وقت؟
متابعة patch آمن لسلسلة picomatch وأدوات ESLint دون downgrade قسري؛ توسيع المتصفحات وقارئات الشاشة والتكبير والأجهزة؛ قياس الأداء بأهداف محددة؛ تحسين تنسيق JSX المكثف مع احترام سياسة التعليقات؛ إضافة فحص أنواع أقوى لأدوات mjs الاختبارية؛ ومراجعة متطلبات التشغيل والأمان إن طُلب نشر عام. هذه مقترحات غير منفذة، وليست ميزات ندعي وجودها أو تصريحًا لإضافة auth أو queues خارج النطاق.
